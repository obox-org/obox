# obox-ext-grill — 穷尽提问

## 职责

**做**：把"简要功能"问成一份可写 spec 的结论集——每个维度都要有**明确结论**或**显式标记的延后**，并全部落进 `notes/grill.md`。

**不做**：**不写任何代码**、不建工程（那是上一步 `obox-ext-init`）、不写 `proposal.md` / spec delta（那是下一步 `obox-ext-proposal`）、不做设计决策（UI 风格与交互细节归 `obox-ext-design`）。

问题格式（中文、单次一问、选项带优缺点、恰好一个推荐置首、一个逃生项）与门禁四选项见 [`docs/extension-workflow.md`](../../docs/extension-workflow.md) 第五、十节。

## 输入与前置检查

| 前置                                                                                              | 缺了怎么办                                                                                                      |
| ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `obox-ext-init` 已定工程：扩展目录 + `openspec/`（`config.yaml` + `specs/` + `changes/archive/`） | 停下报错："未找到 `<工程>/openspec/`，请先回到 `obox-ext-init`"，**不要**自己建工程                             |
| 本次 change 的 `change-id`（`openspec/changes/<change-id>/` 或其 `.openspec.yaml`）               | 停下报错并让用户回到 `obox-ext-init`：`init` 第 4 步必已建好 change 目录与 `.openspec.yaml`，不在这里新建或改名 |
| 简要功能一句话（init 第 1 步的结论）                                                              | 先问用户要这句话，再开始 grill                                                                                  |
| 若干**事实**：扩展形态、既有 `manifest.json`、既有代码与 `docs/spec/**`                           | **自己查**（读文件、跑命令、派子代理），不要把可查的事当问题问用户                                              |

## 步骤

1. **建问题清单**。先通读：`manifest.json`、入口文件、`docs/spec/**`、既有 `openspec/specs/**`。按下表每个维度列 0–n 个问题，只保留**答案会改变实现或改不了就得返工**的问题；能自己查的删掉。
2. **逐条提问**。每次一个维度只问一个问题：`ask_user_question`，2–4 个具体选项、每个选项写明优缺点、恰好一个「推荐」置首、外加一个「其他（我来说明）」。用户答完再决定下一个问题（答案常使后续问题作废）。
3. **登记结论**。每问一次就地追加到 `openspec/changes/<change-id>/notes/grill.md`：维度 → 问题 → 结论（或"显式延后"）。不攒到最后补写。
4. **收口**。清点下表，逐维度落到三态之一：**已关闭**（结论明确到能写 requirement；关闭方式为 `用户答复` 或 `代理查得事实`）／**显式延后**（写明延后到哪一步、谁承担风险）／**未决项**（仍缺信息，列出要谁提供什么）。未决项不为空时不得进入门禁的"通过"分支。

### 覆盖维度清单（逐条过，不跳）

每行都要落一个**关闭方式**：`用户答复`（问了用户）／`代理查得事实`（自己查到了，记出处）／`显式延后`（写明延后到哪一步、谁承担风险）。**凡能由代理查得事实的维度不必提问**——直接查、直接记；只有"答案会改变实现且查不到"的才走 `ask_user_question`。

| 维度           | 必须问出什么                                                         | 关闭方式（默认） |
| -------------- | -------------------------------------------------------------------- | ---------------- |
| 用户与场景     | 谁在用、在什么时机用、一次典型使用的完整路径                         | 用户答复         |
| 痛点与现状     | 现在怎么做、为什么不够、不做的代价                                   | 用户答复         |
| 成功标准       | 可验证的验收条件（能被后续 spec 的 scenario 直接吃下）               | 用户答复         |
| 范围           | 本轮的**功能边界**：哪些能力必须在，哪些明确不做                     | 用户答复         |
| 非目标         | 明确排除的东西（防止实现时扩大范围）                                 | 用户答复         |
| 数据来源与语义 | 数据从哪来、字段含义、单位、空值、时效、是否持久化                   | 代理查得事实优先 |
| 权限与安全     | 需要哪些宿主能力（文件 / 进程 / 凭据 / IPC）、涉不涉密、失败如何隔离 | 代理查得事实优先 |
| 前端与后端交互 | 界面在哪（App 卡片 / 树视图 / 命令 / 设置页）、消息通道与载荷形状    | 用户答复         |
| 兼容与迁移     | 与既有版本、既有数据、既有配置的兼容；升级与回滚                     | 用户答复         |
| 异常与重试     | 失败表现、重试策略、幂等性、用户可见的错误文案                       | 用户答复         |
| 可观测性       | 日志、状态栏提示、错误上报；出问题怎么定位                           | 代理查得事实优先 |
| 交付与分发     | 只本地用还是 `.oix` 分发；要不要跟随宿主更新                         | 用户答复         |

### 停止判据

维度表**每一行**都已落到三态之一。**不接受**"看起来够了"：某维度既没有结论也没有显式延后，就还没问完。

## 产物与路径

`<扩展工程>/openspec/changes/<change-id>/notes/grill.md`，结构固定：

```markdown
# grill — <一句话需求>

## 逐条问答摘要

### Q1（用户与场景）…

- 问题：…
- 结论：…（或「显式延后」）

## 已关闭

| 维度 | 关闭方式 | 结论 | 依据 |
| ---- | -------- | ---- | ---- |

## 显式延后

| 维度 | 延后到 | 理由与承担者 |
| ---- | ------ | ------------ |

## 未决项

| #   | 缺什么 | 谁来提供 | 阻塞哪一步 |
| --- | ------ | -------- | ---------- |
```

**完成判据**：文件存在；维度表 12 行**每行都标了关闭方式**（`用户答复` / `代理查得事实` / `显式延后`），且 12 行合计归入"已关闭"（前两者）与"显式延后"两节；"未决项"为空（或已逐条说明为什么可以带着进门禁而不能带着进 proposal）。

## 门禁

`ask_user_question` 问「本步产出是否符合要求？」，选项恒为：

1. **通过，自动进入 `obox-ext-proposal`（推荐）** —— 下一步把 grill 结论汇总成 `proposal.md` 与 spec delta；选它时**读 `skills/obox-ext-proposal/SKILL.md` 并照做**。
2. **部分修改后重跑本步** —— 用户说明哪个维度还要追问。
3. **回到上一步 `obox-ext-init`** —— 从源头改工程身份 / 形态 / change，再重跑本步。
4. **暂停** —— 用户先人工检查。

## 完成判据

- `notes/grill.md` 存在，四节齐全（逐条问答 / 已关闭 / 显式延后 / 未决项）；
- 12 个维度逐行有归属与关闭方式，无"未过问"的行，也没有"能查却问了用户"的行；
- 每次提问都真的走过 `ask_user_question`（不是正文罗列问题），且每问都带优缺点与推荐项；
- 本人**未改动**任何代码文件（`git status` 里只有 `notes/grill.md` 这一个新文件）。
