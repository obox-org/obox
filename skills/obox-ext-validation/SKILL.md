# obox 扩展开发 · 第 5 步：规格校验

## 职责

**做**：只读校验 `spec delta` + `design.md`，产出三档结论与修复意见。
**不做**：不改 spec / design / 代码，不替用户决定"这算不算问题"，不提前跑第 6 步的任务拆解。

公共约定（九步链表、目录布局、双标识、API 公共位置、门禁四选项、问题三档、提问规范）见 `docs/extension-workflow.md`，**逐条照做，不在此复述**。

## 输入与前置检查

| 输入       | 路径                                                      |
| ---------- | --------------------------------------------------------- |
| spec delta | `openspec/changes/<change-id>/specs/<capability>/spec.md` |
| 设计文档   | `openspec/changes/<change-id>/design.md`                  |
| 上游上下文 | 同目录 `proposal.md` 与 `notes/grill.md`                  |

开工前逐项确认，**任一项缺失就报错并让用户回到对应步骤，不得继续**：

1. `spec delta` 存在，且含 `## ADDED/MODIFIED/REMOVED Requirements` 与小节级 `#### Scenario:`（正好 4 个 `#`）。
2. `design.md` 存在，且覆盖交互逻辑与 UI 视觉规范。
3. `change-id` 满足官方约束：小写字母/数字/单个连字符。
4. 读了 `docs/extension-api/` 下的 `api-reference.md` / `manifest-reference.md` / `themes-settings.md`——引用时给具体章节或 `文件:行`，不复制副本、不凭记忆。

## 步骤

### 1. 逐条比对 spec delta 与 design

**九个维度每维过一遍，逐条给出发现或"无"**：

| 维度           | 要抓到什么                                                       |
| -------------- | ---------------------------------------------------------------- |
| 互相冲突       | spec 与 design 对同一行为给出不同说法                            |
| 需求遗漏       | spec 有而 design 无落点，或 design 有而 spec 无来源              |
| 不可验收       | 写不出判据："友好""流畅""合理"这类无法证伪的措辞                 |
| 与宿主不符     | 用了不存在的 API、贡献点、主题 token；违反了 manifest 校验规则   |
| 权限与安全     | 用户扩展跑在 Extension Host Process（与 UI 不同进程）但**仍无沙箱**（ADR-0015：能力封装不是安全边界，宿主模式下还有完整 Node）；越权读写、明文存密钥 |
| 数据语义与迁移 | 落盘格式、覆盖安装与升级时的旧数据、字段可空性                   |
| 行为冲突       | 与既有扩展或既有能力抢同一命令 id、导航位、快捷键                |
| 兼容与异常     | 平台差异（托盘/自启/通知仅 Windows）、空数据、错误路径、失败回滚 |
| 可维护性       | 与既有扩展写法不一致、引入运行期依赖                             |

**完成判据**：九个维度都有结论（含"无"）；每条发现都定位到 `文件:行` 或章节锚点，并写出影响与修复意见。

### 2. 核实 API 真实性

design 引用的每个 API 方法、贡献点字段、主题 token，到 `docs/extension-api/api-reference.md`（「方法总览」起）、`manifest-reference.md`、`themes-settings.md` 的对应章节核对存在性与参数形状。核对不上的记入"与宿主不符"。

**完成判据**：design 里出现的 API 与字段 100% 核对过，**零"凭记忆写 API"**。

### 3. 跑官方校验（CLI 可用时）

`openspec --version` 成功 → `openspec validate --strict`；失败项并入结论。

**完成判据**：跑过并把原始输出摘进产物；**CLI 不可用时跳过，并在产物里写明"未跑官方校验"**。

### 4. 归入三档并排序

按 `docs/extension-workflow.md` §六 分档，**每条附 `文件:行` 或章节锚点 + 修复意见**：

- **严重问题**：会导致实现错误、数据丢失、安全问题或与 spec 直接冲突 → 逐条一问。
- **普通问题**：影响质量或可维护性但不阻断 → 合并为一次多选。**"证据不足"（无自动测试 / 未实机验证）归这一档**，并在条目里写明缺的是哪类证据。
- **一般建议**：风格与可选改进 → 默认只登记。

**完成判据**：每条发现都落在恰好一档；严重问题都能说清"照现状实现会错在哪"；证据不足项没有升档也没有降档。

### 5. 落盘

写入 `openspec/changes/<change-id>/notes/validation.md`：结论摘要（三档计数）→ 严重问题逐条 → 普通问题清单 → 一般建议清单 → 已核对的 API 章节清单 → 未决项。

**完成判据**：文件存在；三档各成节；每条都有锚点与修复意见。

### 6. 门禁

见下。**有严重问题时**，除四选项外**必须再追问一个问题**："回 `proposal` 还是 `design`？"，选项写明各自代价。

**有"证据不足"项时**，除四选项外**必须单独追问一次**"是否接受带着未验证项继续？"——把「接受风险并登记」从「暂停」里显式提出来（选项：接受风险并登记（推荐）/ 回上一步补验证 / 暂停 / 其他（我来说明））。

## 产物与路径

`openspec/changes/<change-id>/notes/validation.md`

## 门禁

用 `ask_user_question` 问「本步产出是否符合要求？」：

1. **通过，自动进入 `obox-ext-task`（推荐）** —— 下一步读 `skills/obox-ext-task/SKILL.md` 并照做，把 spec delta + `design.md` 拆成 `notes/tasks/<nn>-<slug>.md` 任务卡与 `tasks.md`。
2. **部分修改后重跑本步** —— 用户说明要改什么。
3. **回到上一步 `obox-ext-design`** —— 回退并重做设计文档。
4. **暂停** —— 用户先人工检查。

被选 1 时**读取 `skills/obox-ext-task/SKILL.md` 并照做**，不依赖 Skill 工具。

## 完成判据

- `notes/validation.md` 已写出，三档结论齐备且每条带锚点与修复意见；
- design 引用的 API 全部核对过；官方校验跑过或已注明未跑；
- 证据不足项已归入普通问题并标明缺哪类证据，门禁上单独追问过一次；
- 门禁问过并拿到用户选择。
