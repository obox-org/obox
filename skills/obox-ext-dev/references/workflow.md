# 扩展开发流程（workflow）

扩展开发**先澄清、再动手**。`SKILL.md` 的流程骨架在此展开；提问一律照 `AGENTS.md` 的提问约定执行。

## 0. 何时走全流程

判据是需求**是否改变对外行为 / 贡献点 / 数据结构**：

| 需求性质                                                                 | 流程                                                                            |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| 改变对外行为、贡献点或数据结构（新功能、API 用法、持久化格式、分发方式） | **全流程**：提问 → spec → 用户确认 → 设计文档 → 开发 → 测试 → 审视 → ADR → 归档 |
| 只改文案 / 样式 / 修单点 bug（不动行为契约）                             | **轻流程**：提问 + 开发 + 测试                                                  |

拿不准按全流程走。

## 1. 阶段一：提问（M1–M8）

八项**每个需求都问**，与需求内容无关；用 `ask_user_question` 逐轮追问。

| #   | 要问出什么                                                                                            | 为什么它决定实现                                                            |
| --- | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| M1  | 类型与落位：内置还是用户扩展；扩展 id 与显示名                                                        | 决定入口语言（TS+Vite vs 纯 ESM JS）、放哪个目录、读哪份 guides、能否被卸载 |
| M2  | 贡献点集合：导航项 / 状态栏项 / 命令 / 树视图 / App 卡片 / 主题 / 设置 schema / 快捷键 / 菜单，要哪些 | 决定 manifest `contributes` 与宿主注册面；少问一项就少实现一块              |
| M3  | UI 形态：Vue 组件 / 自带 HTML 静态页 / App 子窗口 iframe / 无 UI                                      | 决定是否引入构建链、视图怎么导出、受 CSP 哪些限制                           |
| M4  | 状态与数据：Memento / sqlite / `api.fs` 文件 / `secrets` / 不持久化；旧数据与旧配置如何兼容           | 决定落盘位置与迁移代码，事后改动代价最高                                    |
| M5  | 外部依赖：无 / `api.ipc` 子进程 / `api.python` 运行时 / `api.net` 网络 / updater                      | 决定打包体积、进程权限与平台差异                                            |
| M6  | 目标平台：Windows / macOS / Linux（托盘、开机自启、通知**仅 Windows**）                               | 决定能力是否可用及降级路径                                                  |
| M7  | 是否需改宿主或新增 API                                                                                | 命中即把范围扩大到主进程/宿主，并改判 ADR 落位（阶段八）                    |
| M8  | 发布与验收：`.oix` 打包 / 版本号 / 更新通道；怎么算做完；是否中英双语（`titleKey` + zh/en 词条）      | 决定交付物清单与验收标准                                                    |

个性化追问（命中才问）：

| 需求特征           | 追问什么                                                                                      |
| ------------------ | --------------------------------------------------------------------------------------------- |
| 不可信第三方代码   | 信任边界：扩展与宿主同进程同上下文、无沙箱（`docs/adr/0015`），需强隔离须改用独立进程或子窗口 |
| 安装 / 卸载 / 升级 | 入口钩子的幂等与失败回滚（覆盖安装会重跑 `install`）                                          |
| 跨扩展调用         | `extensionDependencies` 声明与命令 id 归属                                                    |
| 大数据量 / 查询    | sqlite 与 `api.fs` 文件的选型及体量上限                                                       |
| 改造已有扩展       | 迁移路径与向后兼容（旧数据、旧 manifest 字段）                                                |
| 性能敏感           | 定时器、事件监听、子进程的常驻开销                                                            |
| 多窗口             | 子窗口不跑扩展代码（`?obox-window=app`），只走 `api.app.onMessage`                            |

三条硬边界：

1. 只实现确认过的内容，**多一个也算越界**。
2. 一旦发现需要新增/修改宿主 API 或主进程能力，**停下来问**用户，并把 ADR 落位改判到仓库 `docs/adr/`。
3. 用户扩展不引入 npm 依赖，内置扩展不新增依赖；要加先问。

提问规范：照 `AGENTS.md` 的提问约定（一次一问、每案写优缺点、恰好一个推荐且置首位、另有「其他（我来说明）」）。

## 2. 阶段二：spec

写到 `tmp/spec/<扩展id>-<短名>.md`（`tmp/` 已 gitignore）。模板：

| 节            | 内容                                                          |
| ------------- | ------------------------------------------------------------- |
| 背景与事实    | 现状与约束；**每条事实带 `文件:行号` 证据**，不写未查证的推断 |
| 目标 / 非目标 | 做什么、明确不做什么（后者防范围蔓延）                        |
| 需求表        | 一条一行，**每条标来源**（哪轮问答 / 哪个 issue）             |
| 交付物        | 逐文件列出新增与修改                                          |
| 验收标准      | 可执行：命令 + 期望退出码或可观察现象                         |
| 风险与未决项  | 每项写处置方式                                                |

## 3. 阶段三：用户确认

**唯一关卡**。用户确认 spec 之前：不许写设计文档，不许开工改代码。用户有异议就回阶段一 / 二迭代。

## 4. 阶段四：设计文档

写到 `tmp/spec/<扩展id>-<短名>-design.md`。模板：决策摘要（spec 每条需求 → 设计落点）/ 文件布局 / 逐文件设计 / 接口与数据 / 迁移 / 测试计划 / 执行顺序与并行切分（写明文件所有权，避免并发写同一文件）/ 验收执行清单（把验收标准落成命令）/ 内容风格约定。

## 5. 阶段五：开发

分支命名、commit 信息、推送与开 PR 照 `AGENTS.md` 的提交约定执行；质量门禁见阶段六。只在设计文档划定的文件所有权内改文件。

## 6. 阶段六：测试

三道都要过：仓库门禁 `npm run typecheck`、`npm run lint`、`npm test`；扩展自带测试（用户扩展用 `node --test`，带 Vue 子应用的另跑构建）；真机运行（`npm run dev`，或装入 `.oix` 后操作实际功能）。**没验证过不许声称完成**，未做实机验证的结论必须标注「未验证」。

## 7. 阶段七：审视

派**独立子代理**对照 spec 与设计文档 review 实现（它读文档与代码，不看开发过程的自我叙述）。它报的每条问题必须**处置**：改掉，或写明为何不改。视角至少含：与 spec 的偏差、越界扩大范围、事实错误、遗漏的边界（错误路径、空数据、并发、平台差异）。

## 8. 阶段八：ADR

三条件命中**任一**才写（都不命中就不写，避免 ADR 噪声）：难以逆转 / 无背景的人会觉得奇怪 / 存在真实取舍。先写 `tmp/adr/<短名>.md`，再按落位表归档：

| 改动性质                            | 落位                                         | 编号           |
| ----------------------------------- | -------------------------------------------- | -------------- |
| 用户扩展                            | `extensions/<id>/docs/adr/`                  | 目标目录内顺延 |
| 内置扩展                            | `src/renderer/src/extensions/<id>/docs/adr/` | 目标目录内顺延 |
| 宿主 / 主进程 / 扩展系统 / 仓库自身 | 仓库 `docs/adr/`                             | 续现有编号     |

## 9. 阶段九：归档并清空 tmp/

`tmp/spec/` → `<开发目录>/docs/spec/`，`tmp/adr/` → `<开发目录>/docs/adr/`（开发目录按阶段八的三级落位确定）。随后**删除整个 `tmp/` 目录**：`tmp/` 已 gitignore，只有归档后的文件才进版本库。
