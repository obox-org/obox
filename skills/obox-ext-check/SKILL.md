# obox 扩展开发 · 第 8 步：验收检查

## 职责

**做**：只读对照 spec delta、`design.md` 与任务卡检查实现，复跑门槛，产出三档结论与修复意见。
**不做**：**纯检查——不改任何代码、测试、spec、design 或任务卡**；不替用户决定放行。

公共约定见 `docs/extension-workflow.md`（§五 门禁、§六 问题三档、§十 提问规范），**逐条照做**。

## 输入与前置检查

| 输入         | 路径                                                      |
| ------------ | --------------------------------------------------------- |
| spec delta   | `openspec/changes/<change-id>/specs/<capability>/spec.md` |
| 设计文档     | `openspec/changes/<change-id>/design.md`                  |
| 任务卡与清单 | `notes/tasks/<nn>-<slug>.md`、`tasks.md`                  |
| 开发回执     | `notes/dev.md`                                            |

开工前确认，**任一项缺失就报错并让用户回到对应步骤**：

1. `notes/dev.md` 存在，且每张卡都有回执（含门槛原始输出）。
2. 工作区**无本次提交**——若已被提交，说明有人越过了 `dev`/`ship` 边界，先向用户报告。
3. `notes/validation.md` 的严重问题都已处置（未处置项要在这里重新抓一遍）。

## 步骤

### 1. 逐条核对 spec delta

把每个 requirement 与每个 `#### Scenario:` 摊开，逐条判定实现落点与测试覆盖：**有实现且有测试** / **有实现无测试** / **无实现** / **实现与需求不一致**，各给 `文件:行` 证据。

**完成判据**：requirement 与 scenario **逐条**有判定，计数与 spec delta 的实际条数一致——**没有"跳过不适用"的条目**，不适用的也要写明理由。

### 2. 核对 design 决策与 UI 规范

逐个决策与每条 UI 规范（零自造色值、只用宿主主题 token、标签列固定宽左对齐、窄窗堆叠、下拉说明写在选项内、模态框只能按钮关闭）到代码里找落点，给 `文件:行`。

**完成判据**：每条决策与规范都有"已遵守 + 位置"或"未遵守 + 位置"，没有只写结论不给证据的条目。

### 3. 查越界

拿实际改动（`git status --porcelain=v1` + `git diff --stat`）对照各卡的**文件所有权**：所有权外出现的文件、以及所有权内的文件却改了不属于该卡的行为，都算越界并逐条列出。

**完成判据**：改动文件集合与任务卡所有权集合的差集已算清并逐条说明；工作区没被本步改动过。

### 4. 复跑门槛（原始输出）

亲手重跑，不采信回执里的转述：宿主 `src/**` → `npm run typecheck`、`npm run lint`、`npm test`；扩展工程 → **仅当它有 `build` 脚本时**才 `npm run build`（清理对象按其构建配置的 `outDir`：`--vue` 脚手架是 `dist/`，`extensions/rdp` / `extensions/webapp` 是 `ui/`），有 `pack` 就跑 `node scripts/pack.mjs`，并跑扩展自带测试；缺 `build` 的扩展按"自带测试 + 清单校验"复跑，并在 `notes/check.md` 写明没跑 build 的原因。

**中文输出编码**：门槛输出要原文粘贴，含中文的 stdout/stderr 在 Windows PowerShell 5.1 下经 `Get-Content` 会显示成乱码——用 `Get-Content -Encoding utf8` 读取，或直接读文件；**粘贴前先确认中文没坏**。

**完成判据**：每条应跑的命令都有本次的原始输出（不适用的写明原因）；**与回执不一致的结果必须显式指明**（复跑不绿是最强证据）。

### 5. 归入三档并写 `notes/check.md`

按 §六 分档，每条附 `文件:行` 或章节锚点 + 修复意见；文件结构：结论摘要 → 严重问题逐条 → 普通问题清单 → 一般建议清单 → 门槛复跑原始输出 → 未决项。

**完成判据**：`notes/check.md` 存在；三档各成节；每条带锚点与修复意见；门槛输出是原文粘贴。

### 6. 门禁

见下。**严重问题存在时**，除四选项外按"立即修复（回 `dev`）/ 改规格或设计 / 接受风险并登记 / 暂缓"**逐条一问**；普通问题合并为一次多选；一般建议默认只登记。

**有"证据不足"项时**（无自动测试 / 未实机验证，归普通问题，见 workflow §六），除四选项外**必须单独追问一次**"是否接受带着未验证项继续？"——把「接受风险并登记」从「暂停」里显式提出来（选项：接受风险并登记（推荐）/ 回 `dev` 补验证 / 暂停 / 其他（我来说明））。

**自动链最多 3 轮**（`check` → `dev` → `check` 记 1 轮），3 轮仍有严重问题就停下交用户裁定，并说明每轮修了什么、还差什么。

## 产物与路径

`openspec/changes/<change-id>/notes/check.md`

## 门禁

用 `ask_user_question` 问「本步产出是否符合要求？」：

1. **通过，自动进入 `obox-ext-ship`（推荐）** —— 下一步读 `skills/obox-ext-ship/SKILL.md` 并照做：交付归档 → 工具归档 → 文档同步 → 提交与发版（发版前单独再问一次）。
2. **部分修改后重跑本步** —— 用户说明要重查哪些条目。
3. **回到上一步 `obox-ext-dev`** —— 严重问题要改代码时选它，修完再回到本步（计入 3 轮）。
4. **暂停** —— 用户先人工检查（含"接受风险并登记"的裁决）。

**有严重问题时**，先逐条按"立即修复（回 `dev`）/ 改规格或设计 / 接受风险并登记 / 暂缓"追问，再走上面四选项。

被选 1 时**读取 `skills/obox-ext-ship/SKILL.md` 并照做**，不依赖 Skill 工具。

## 完成判据

- spec delta 的 requirement 与 scenario 逐条有判定与证据，design 决策与 UI 规范逐条核对过；
- 越界改动已查清，门槛已复跑并留原始输出（含与回执的差异说明）；
- `notes/check.md` 三档齐备，严重问题已逐条追问；证据不足项已归普通问题并标明缺哪类证据，门禁上单独追问过一次；
- 本步**未改动任何代码**；门禁问过并拿到用户选择。
