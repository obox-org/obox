# 扩展信任模型与身份守卫（S2）

## 背景

审计提出：所有扩展面向的主进程能力 IPC 都把 `extId` 当普通参数接收，未校验来源，因此"任意扩展可伪造别的扩展 id 读写它的文件/数据库/密钥"。最初设想是"守卫从请求的 frame URL 推导真实 extId"。

**该设想在本架构下不成立**，落地前必须纠正：

1. 扩展入口是被宿主**动态 `import` 进主窗口渲染进程**的 ESM 模块（`core/loader.ts`），与宿主、与彼此**同进程同上下文**；
2. 因此能力调用到达主进程时，`senderFrame` 对**所有扩展都是同一个窗口**（dev 为 `localhost:5173`，打包为 `file://…/index.html`），没有任何按扩展可区分的来源信息；
3. 扩展本身可直接访问 `window.api` 与 `window.events`（`preload` 经 contextBridge 暴露给整个渲染进程），因此"绕过扩展 API 直接调能力"本来就不需要技巧。

结论：**同上下文架构下，主进程无法区分是哪个扩展在调用，也无法阻止它冒用他人的 id。** 任何 nonce/私有通道方案只是抬高成本（同一模块缓存下的动态 import 仍可读到宿主状态），不构成边界。

## 决策

1. **不把守卫当安全边界**：新增 `src/main/extGuard.ts`，定位为**误用防护**，只做三件事：
   - id 规范化收敛到一处（规则与 `.oix` 安装目录名一致：`^[a-z0-9][a-z0-9._-]*$`，拒绝分隔符、`..`、空串）；
   - 在 main **确实掌握真值**的场景做成员校验（已知集合 = 用户扩展目录扫描 ∪ `--debug-extension` 声明的 id ∪ 安装成功后的登记，卸载后移除）；
   - 稳定错误码（`invalid-extension-id` / `unknown-extension`），消息带 `[code]` 前缀便于 grep 与展示，统一拒绝语义。
2. **数据面 handler 只做"格式 + 路径包含"校验，不做成员校验**：内置扩展随应用打包、不在 userData，主进程无法枚举；若在数据面强制成员校验，要么挡掉内置扩展的合法调用，要么得让渲染进程上报 id 集合——那等于让被检查方自己报身份，收益为零。故数据面的隔离仍由既有的路径规则承担（相对路径解析到 `userData/extensions/<id>/data`、拒绝绝对路径与穿越）。
3. **成员校验用在 main 掌握真值的生命周期路径**：例如"只对已安装扩展执行卸载钩子"（`extensions:run-uninstall-hook`）；卸载路径用规范化（不用成员校验，避免集合陈旧时挡掉合法卸载）。
4. **限额不集中**：timer 秒数上限、fs.watch 数量上限、net 响应体上限、sqlite SQL 白名单留在各自模块——它们是**各自资源语义**的一部分（batch C/A 已落地），集中到守卫只会让守卫变成上帝对象，并制造跨模块耦合。守卫只负责身份与错误码。
5. **真隔离的方向记在此处、本期不做**：把扩展宿主移入独立进程（`utilityProcess`/子进程），能力经消息桥而非直接 IPC；代价是重做加载器、消息桥、热装卸与调试扩展链路，远大于本规格范围。

## 后果

- **好处**：id 解析与拒绝语义单点化（可单测的缝隙）、生命周期路径有了成员真值校验、文档不再暗示"扩展被隔离"。
- **代价/局限**：**恶意扩展仍可冒用同上下文内其他扩展的 id**——这是架构决定的，不是本决策的疏漏；需要真隔离时按上条第 5 点另立规格。
- **不变量**：任何 handler 都不得声称"已做过安全校验"；错误码只表达误用类别，不表达权限。
