# 设计问答约定：选项化提问（优缺点 + 推荐标签）

## 背景

`/grilling`、`/to-spec` 这类设计会话中，AI 代理原先用**散文**提出决策问题（"我推荐 A，因为…；不过 B 也有道理"）。实际使用中暴露出三个问题：

1. **备选方案不可见**：写进正文的替代方案容易被长篇分析淹没，用户只能看到结论，看不到"还有哪几条路、各自代价是什么"；
2. **决策不可审计**：事后回看（或新会话接手）无法判断"当时考虑过什么、为什么排除"，只能看到最终选择；
3. **回答成本高**：用户需要用自然语言复述选择，容易产生歧义（"用第一种吧"指代不明）。

同时 `AGENTS.md` 已有强制约定：需要决策时**单次只提一个问题、用中文、用 `ask_user_question` 工具、按回答迭代推进**。本 ADR 在该约定之上补齐**格式**要求。

## 决策

**每个决策问题都必须通过 `ask_user_question` 提出，并且：**

1. 提供 **≥2 个具体选项**（不是"是/否"式模糊确认，而是可执行的方案分歧点）；
2. **每个选项都写明优缺点**（写在选项说明里，包含代价与适用条件，不能只写好处）；
3. **恰好一个选项标记为「推荐」并置于首位**（`选项名（推荐）`），其余选项保持中性描述；
4. 另提供一个 **"其他（我来说明）"逃生选项**，避免选项集合本身限制了真实存在的第三条路；
5. **仍保持单次一个问题**（遵循 `AGENTS.md`）：收到回答后再据其推进下一个问题，不一次抛出整个问题清单；
6. 问题正文里可以（也应该）包含**已经查明的事实**——事实是代理的职责（自己查或派子代理），决策才是用户的；不要把"你能帮我查一下 X 吗"当问题问用户。

## 后果

- **好处**：权衡被显式摆出、每个决策留痕可审计、用户回答成本低（点选即可）、新接手者能看到"考虑过哪些替代方案"；
- **代价**：比散文提问啰嗦；选项设计有引导性（锚定推荐项）——因此要求优缺点**如实且平衡**，推荐项的理由必须写在说明里而不是靠排序暗示；
- **约束**：一次一问意味着问题多的议题需要多轮；轮次多比"一次性堆问题导致误答"更划算。

## 考虑过的替代方案

- **散文提问**（否决）：备选方案与代价不可见，决策无法审计。
- **一轮抛出全部问题**（否决）：违反 `AGENTS.md` 的"单次只提问一个问题"，且用户容易漏答或误答。
- **只写一份提案文档让用户批注**（否决）：决策散落在长文里，难以逐条确认与追踪。
