# Design

## Context

见 `proposal.md - Why`。设计相关的现状与约束：

- 卡片地址的**唯一来源**是扩展在 `api.app.register({ url })` 里给的值（持久化在 `appStore`，子窗口经 localStorage 快照读取）。宿主目前原样塞进 `<iframe src>`（`src/renderer/src/AppWindow.vue`）。
- 外壳 CSP（`src/renderer/index.html`）为 `default-src 'self' app:`，`frame-src` 回落到它 ⇒ 只有 `self` 与 `app:` 可作 iframe 源；`file:` 一律被拒且**不触发可用的错误事件**。
- `app://` 响应**没有 CSP 头**（只有外壳有），所以归一化到 `app://` 是唯一"既能加载、又不打穿 CSP"的方向。
- 主进程侧已有 `resolveAppUrl`（`src/main/appUrlCore.ts`）：`app://extensions/<目录名>/…` 由它按 `systemRoot`/`userRoot` 解析，越界返回 403/404。归一化只需产出**形状正确**的 `app://` 地址，落地校验仍由主进程负责。
- 子窗口（`?obox-window=app`）不激活扩展、不加载 `host`，因此**拿不到**扩展的安装目录名，只能依赖地址形状判断。

## Goals / Non-Goals

**Goals:**

- 已安装的旧扩展（`file://` 卡片地址）无需重发即可打开。
- 任何打不开的地址都变成"看得懂的失败"，而不是白屏。
- 归一化/判定逻辑可单测（纯函数，不依赖 DOM、electron、网络）。
- 不扩大任何安全边界。

**Non-Goals:**

- 不放宽 CSP 去允许 `file:`（这会打穿渲染进程同源边界）。
- 不替扩展改写源码或磁盘文件。
- 不处理"归一化成功但目标文件不存在"的 404——那属于扩展自身打包问题，诊断态只提示查看地址与扩展目录。

## Decisions

### D1. 归一化放在渲染侧（`AppWindow` 之前），而非主进程

- **选择**：新增纯函数模块（渲染侧 `core/`），在 `iframeSrc` 计算时调用；主进程 `app://` 解析保持唯一权威。
- **理由**：卡片 url 的消费点在渲染侧（AppWindow 直连 iframe），主进程根本看不到它；若改由主进程介入，需要多一条 IPC 往返并让子窗口依赖主进程，收益为零。
- **替代方案**：① 在 `app.register` 时校验并拒绝（否决：会让已安装扩展直接注册失败，等于把白屏换成"卡片消失"，且需要扩展重装）；② 主进程在 protocol 层把 `file:` 重写（否决：protocol 只处理 `app://`，且 `file:` 请求根本不进这个 handler）。

### D2. 只归一化"形状可判定"的 `file://`

- **选择**：路径中出现 `…/extensions/<目录名>/<相对路径>` 段时，映射为 `app://extensions/<目录名>/<相对路径>`；调试扩展目录需要显式登记（子窗口拿不到 `--debug-extension` 表，走"当前地址所在目录与已注册调试目录一致"的判定只在主窗口可用 ⇒ 子窗口内的 `file://` 调试目录**不归一化**，改走诊断态并提示用 `app://debug/<id>/`）。
- **理由**：宁可给出准确诊断，也不要猜错——猜错会把用户送到 404 页面，比白屏更难排查。
- **替代方案**：① 用正则匹配任意 `file://` 并一律转 `app://`（否决：目录名对不上会 404，且可能把非扩展目录映射进扩展根）；② 查安装目录表（否决：子窗口没有扩展表）。

### D3. 诊断态用既有空态容器，而不是新窗口或对话框

- **选择**：复用 `.app-window-empty` 容器渲染诊断块；overlay 仍保持"不画任何像素"（透明窗体），只在控制台告警。
- **理由**：App 卡片窗口本来就是"标题栏 + 内容区"，诊断放内容区最自然；overlay 的透明语义已有明确约定（空态文字也是像素），不能破坏。
- **替代方案**：另开一个错误窗口（否决：多窗口管理成本，且用户点一次出两个窗口）。

### D4. iframe 底色走 token，同时保留页面自身可覆盖

- **选择**：`.app-frame { background: var(--bg, #1e1e1e) }`。
- **理由**：`var()` 有兜底，主题缺失时退回暗色；扩展页面自己的 `<html>/<body>` 背景仍覆盖它（iframe 文档自身的绘制优先）。
- **替代方案**：保留白色（否决：正是当前"白屏"的观感来源）；用 `transparent`（否决：父容器是窗体背景，深色主题下会露出一块未定义色）。

### D5. 告警按"窗口 + 地址"去重

- **选择**：模块内维护 `Set<string>`，同一次页面生命周期内同一地址只 warn 一次。
- **理由**：主题/语言切换会触发重算，不去重会刷屏（历史先例：`[i18n]` 缺 key 已按同样方式去重）。
- **替代方案**：每次判定都 warn（否决：刷屏后真正有用的第一条被淹没）。

## Risks / Trade-offs

- [归一化把旧地址映射到错误目录 → 404 而不是白屏] → 诊断态在 404 时仍可用（iframe 载入主进程的 404 响应），且 warn 里同时打印原始与归一化地址，便于对照；归一化只在路径含 `extensions/<段>` 时触发。
- [子窗口无法归一化 `file://` 调试目录] → 明确走诊断态，提示改用 `app://debug/<id>/…`（这是可执行的修复指引，不是死路）。
- [用户已经习惯"白屏=等功能修好"] → 诊断态会显得"多了一个页面"；缓解：文案明确写"扩展页面未能加载"并提供原始地址，便于贴给扩展作者。
- [改成 `var(--bg)` 后，某些扩展页依赖"父层白色"做透出] → 风险低（iframe 内文档的 body 背景通常已自绘）；若真出现，扩展显式设置 `body { background: #fff }` 即可覆盖。

## Migration Plan

1. 纯新增逻辑（归一化 + 诊断），默认路径（`app://`）零行为变化 ⇒ 无灰度风险。
2. 已安装旧扩展在升级后**立即**恢复（不需要重装），这是本次的主要收益。
3. 回滚：还原 `AppWindow.vue` 与删除新模块即可；无数据迁移、无持久化字段变更。

## Open Questions

- 无。调试扩展在子窗口内的 `file://` 归一化被显式排除（见 D2），不阻塞后续按需扩展。
